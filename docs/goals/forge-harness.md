# Forge Harness 목표 상태

Forge Harness는 사용자가 승인한 전체 개발 목표를 작업관리, 검증, 전달과 세션 인계까지 끊김 없이 수행한다. 이 문서는 제품의 목적과 완료 상태를 정의하며, 상세 계약과 적합성 기준은 [제품 명세](../spec.md)를 따른다.

## 목표와 정본

- 전체 목표는 목적, 완료 기준, 승인된 범위, 남은 작업, 정책과 근거를 가진다. 제어면은 목표의 revision과 이력을 원자적으로 보존한다. 단위 하나의 완료는 전체 목표 완료가 아니다.
- 정본·사용자 결정·현재 코드와 작업관리 상태가 범위를 정한다. 계획 변경과 작업 추가는 기존 승인 범위 안에서 기록하며, 실제 범위·권한 변화는 사용자 지시와 정책에 따라 처리한다. 이전 단위, 실패와 부작용 이력을 지우거나 새 단위로 우회하지 않는다.
- 목표 완료는 남은 작업이 없고 모든 완료 기준이 유효한 수용·검증 근거에 연결될 때만 기록한다. 실제 외부 입력, 사용자 중지, 인증·권한·크레딧·외부 승인 또는 같은 원인 재시도 상한은 이유와 객관적인 재개 조건을 보존한다.

## 세션과 실행 환경

- 하나의 세션은 합의된 작업 범위를 맡는다. 자동 압축, 구현·검증 전환, 계획 조정 또는 단위 경과만으로 새 세션을 만들지 않는다. 작업 범위·권한·독립 리뷰 책임이 실제로 달라질 때 분리한다.
- 세션 시작 시 현재 정책과 실제 가용성을 바탕으로 작업의 종류·난도·위험에 맞는 provider, 계정, 모델과 effort를 선택한다. 선택 가능한 모델 이름은 제품 코드에 고정하지 않으며, 이미 시작한 세션의 모델은 바꾸지 않는다. 개인·회사 계정과 사용자 작업을 섞지 않는다.
- Codex와 Claude Code의 목표 지원을 해당 호스트의 네이티브 `/goal` 명령 또는 동등한 공개 목표 API로 설정한다. 일반 초기 프롬프트나 화면에 붙여 넣은 텍스트는 목표 생성의 증거가 아니다. 호스트가 적용·신뢰를 요구하면 그 경계를 지키며, 확인할 수 없으면 목표 강제가 활성화됐다고 주장하지 않는다.
- cmux에서는 정확한 대상·입력란을 확인하고 목표 명령을 입력·제출한다. 붙여넣기 완료, 키 전송, 큐 수락과 목표 활성은 다른 사건이다. Orca에서는 제공된 명령과 재시도 식별자를 사용한다. 어느 실행기에서도 실제 native 목표 상태, 정확한 요청과 그 뒤 작업 착수를 확인한 영수증이 필요하다.
- 이미 열린 사용자 세션·셸·오케스트레이터는 임의 종료하지 않는다. 검토 세션은 독립적으로 증거와 변경을 확인하며, 수신과 원래 소유자 종료는 각자의 정확한 runtime·세션·incarnation·작업 경로·native 식별자로 검증한다. 이름 변경, 창 배치, 화면 상태만으로 동일성을 판단하지 않는다.

## 작업 단위와 인계

- 범위, 구현, 결정적 게이트, 정책에 따른 독립 리뷰, 수용, 전달과 작업관리 반영을 하나의 단위 수명주기로 기록한다. 스킬은 하나의 책임만 가지며 파일·런타임 부작용은 분리된 제어면 스크립트가 수행한다.
- 승인된 범위 안의 다음 작업이 같은 세션의 책임이면 같은 세션에서 계속한다. 다른 소유자나 독립 리뷰가 필요하면 정확한 목표·정본·정책·인계와 완료 조건을 다음 세션의 네이티브 목표에 지정한다.
- 완료, 실제 차단 또는 명시 중단 시 해당 lifecycle 스킬이 스크립트를 호출해 결과와 필요한 인계의 불변 참조를 만든다. 같은 세션에서 계속하는 단위 완료는 단위 결과를 기록하고 목표를 유지하며 기동·수신·종료 효과를 만들지 않는다.
- 실제로 승인된 소유권 이전이나 리뷰 반환에는 수신자의 목표 활성·작업 착수와 원래 소유자의 정확한 종료를 확인한다. 인계는 목표, 결정, 변경, 검증, 남은 일, 다음 첫 행동을 보존한다. 전체 목표 완료나 수신자가 없는 실제 차단은 successor를 만들지 않고 결과·차단 이유·재개 조건을 사용자에게 보고한다. 자동 종료가 허용된 관리 worker만 별도로 신원을 확인해 닫는다.
- 종료 확인은 살아남는 제어면이 수행한다. 마지막 terminal이 사라진 경우에도 관련 없는 workspace나 surface를 닫지 않는다. 불확실한 기동·전달·종료는 원래 effect와 native 식별자를 재관찰하며 중복 실행하지 않는다.
- 호스트의 중단 명령과 훅 신뢰 설정을 존중한다. 목표 지원이 실행을 계속할 수 없는 실제 차단, 사용자 일시중지 또는 한도에 이르면 그 상태를 보존하고 재개 조건을 보고한다. 자동 압축은 실패나 새 단위가 아니다.

## 정책·게이트·수용

- 정책은 출처와 사용자 권한을 보존한다. 프로젝트에서 승인한 전달 정책은 push, PR 또는 merge까지 적용되며 설치만으로 외부 효과 권한이 생기지 않는다. 활성 단위에 대한 명시적인 정책 변경은 공개 제어면이 이전 값과 승인 근거를 보존하고 안전한 경계에서 적용하며, 수용 대상이나 권한이 달라지면 재검증한다.
- 실제로 구성된 필수 검사와 각 수용 기준은 진짜 실행 결과로 증명한다. 대상 소스·설정·lockfile·명령·도구가 같은 기존 결과는 재사용하며, 다른 입력이나 조건의 결과는 재사용하지 않는다. 검사가 없는 프로젝트에서 존재하지 않는 타입체커나 빌드를 통과로 표시하지 않는다.
- 적용되지 않는 검사는 실제 프로젝트 정본과 불변 검증 대상에 결속된 적용 여부 근거로 구분해 기록한다. 해당 근거는 통과·수용 기준 커버리지로 사용하지 않는다. 누락·위조·오래된 구성, 실패·미실행된 필수 검사와 미커버 기준은 차단한다. 적용 여부의 판단과 정책이 요구하는 독립 검토를 우회하지 않는다.
- 제어면은 게이트 입력과 결과를 독립적으로 검증하며 실행 전후와 최종 수용 시 대상의 동일성을 확인한다. 실행 중 바뀌었다 복구된 입력도 통과 근거가 되지 않도록 검사 대상을 불변 스냅샷에 결속하거나 동등하게 무결성을 입증한다. 변경 또는 판별 불가 시 같은 게이트를 안전하게 재검증한다.
- 리뷰의 `ship`은 동일 head와 내용 fingerprint의 증거에만 유효하다. 리뷰 지적과 재검증은 이력을 보존하고 공개 제어면으로 해소한다. merge는 수용이 고정한 head에서만 수행한다.

## 복구·배포·도그푸딩

- 사용자 관리 플러그인 결함은 원인 서명이 같은 기존 이슈를 확인한 뒤 재현, 기대·실제 동작과 진단을 정본 이슈에 기록한다. 같은 서명의 재시도 상한을 지킨다.
- 이 프로젝트의 하네스 선행 결함은 원 작업의 파일·상태·증거를 보존하고 별도 워크트리에서 원본 수정, 회귀 검증과 정책이 요구하는 독립 리뷰를 마친다. 공식 배포본을 배포·설치·확인한 뒤 원래 단위의 실패한 공개 CLI 지점부터 재개한다. 설치 사본의 직접 패치와 수동 상태 편집은 하지 않는다.
- 전달 정책에 따라 정확한 수용 head를 push·PR·merge하고 공식 버전을 게시한다. 설치된 Codex와 Claude Code 플러그인의 실제 버전과 수정 포함 여부를 확인한다. 그 버전으로 소비 프로젝트의 기존 작업관리·인계를 계속한다.

Forge는 독립 제품이며 다른 애플리케이션의 프로필·승인 체계, 전용 데이터베이스나 daemon을 정본 또는 필수 런타임으로 요구하지 않는다.
